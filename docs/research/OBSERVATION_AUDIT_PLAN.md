## 감사 1 — 응답 도착 간격의 측정 의미

### 질문

- Q1-1. `arrivals_s`가 기록하는 사건은 정확히 무엇인가
- Q1-2. 조각 1개 = token 1개 대응이 **당시 자료로 검증**되었는가
- Q1-3. baseline / injection window / spike / 동시성의 정확한 정의
- Q1-4. 수준별 88.5 / 359.6 / 1177.2 ms와 100.9 / 372.6 / 1191.7 ms의 재현
- Q1-5. "1 ms 이내 동시"가 시작 시각 차·종료 시각 차·구간 교집합 중 무엇인가
- Q1-6. 대조 3회의 큰 간격 발생 시각과 원 `PARTIAL` 판정의 보존

### 재집계 정의 (계산 전 고정)

| 이름 | 정의 |
|---|---|
| arrival | probe가 기록한, **비어 있지 않은 `choices[0].text`를 가진 SSE 조각의 client 수신 시각** |
| interval | 연속한 두 arrival의 `(start, end, gap)` |
| injection window | `[injection.sent_s, injection.done_s]` (client 측 시각) |
| in-window interval | `end > sent_s and start < done_s` (**중첩**) |
| baseline | in-window가 **아닌** interval의 gap 중앙값 (bystander별) |
| spike | in-window interval 중 gap 최대 (bystander별) |
| **중앙값 적용 순서** | **① bystander 4개에 대한 중앙값(run 내) → ② 반복 3개에 대한 중앙값(수준 내)**. 이 순서를 고정하고 역순도 함께 산출해 차이를 보고한다 |
| 동시성(원 기준) | `max(spike_start) < min(spike_end)` — **공통 교집합의 비어 있지 않음** |

### Q1-2의 판정 규칙 (계산 전 고정)

- **검증됨**으로 부르려면: 조각 수와 생성 token 수의 일치 **외에** 조각별 token 수를
  직접 확인한 자료가 있어야 한다
- 그 자료가 없으면 **논문 명칭을 "streaming 응답 도착 간격"으로 유지**하고
  "token 간 간격"이라 쓰지 않는다

### Q1-5의 판정 규칙 (계산 전 고정)

전 9 run에 대해 **세 값을 각각 산출**한다.

1. `max(spike_start) − min(spike_start)` (시작 시각 차)
2. `max(spike_end) − min(spike_end)` (종료 시각 차)
3. `min(spike_end) − max(spike_start)` (공통 교집합 폭)

**공통 교집합의 존재와 경계 시각의 일치를 구분해 보고한다.**

### 질문

  작은 잔여 계산량에서의 사용이 관측인지 외삽인지
- Q2-6. 사후 v2 보정의 ITL 합의 실제 정의와 0.565–0.855 → 0.973–1.039의 집계 경로

### Q2-3의 판정 등급 (계산 전 고정)

| 등급 | 부를 수 있는 조건 |
|---|---|
| **순수 device 실행시간** | 지표가 device 호출 구간만 재고 대기·scheduler·host 처리를 포함하지 않음이 소스로 확인 |
| **서버 측 prefill 경과시간** | 서버 내부의 시작–종료 경과이며 대기·scheduler 시간이 포함될 수 있음 |
| **배타 점유시간의 근사** | 위에 더해, 그 구간에 다른 세션의 decode가 진행되지 못함이 별도 관측으로 뒷받침 |

**세 등급 중 소스와 원자료가 지지하는 가장 좁은 것을 채택한다.**

### Q2-5의 구분 (계산 전 고정)

- `T(L) − T(L−C)`: 길이 `L`까지의 전체 prefill에서 앞의 `L−C`를 뺀 **증분**
- `T(C)`: 길이 `C`짜리 **독립 prefill**
- 두 값은 `ceil(·)` 항과 drift 항 때문에 일반적으로 다르다. **기존 코드가 어느 쪽을
  쓰는지 소스로 확인**하고, 적합 구간 `[500, 6000]` **밖**의 입력에 쓰이면
  **외삽으로 표시**한다

## 감사 3 — 용량 개입에서 간섭의 직접 확인 가능성

### 대상

[TASK35](TASK35.md) N=8 `BASE` → `BATCHONLY` 3반복. **[TASK58](TASK58.md)이 쓴 것과
같은 자료만** 쓴다.

### 절차 (순서를 고정한다)

1. **먼저 목록화**한다 — 병행 세션별 streaming 시계열 / 요청별 prefill 시작·종료
   시각 / 그 시점의 decode 대기 세션 수가 **저장되어 있는가**
2. **시계의 종류·해상도·정렬 가능성을 확인**한다.
   **1초 해상도 로그에서 ms 수준 동시성을 복원하지 않는다**
3. 자료가 허용하면 요청별 prefill 시간과 병행 세션 중첩을 집계한다.
   허용하지 않으면 **"직접 측정 불가"로 마감**한다
4. 전체 N이나 decode step 전체의 평균 running을 prefill 시점의 세션 수로 대체한 값은
   **직접 관측으로 보고하지 않는다**
5. 모형 추정을 낸다면 **실측과 별도 표로 분리**한다. 전체 token 감소량만으로 타 세션
   지연 감소를 계산하지 않는다
6. 단위 `s`(장치 점유)와 `session·s`(누적 대기)를 구분하고 **중복 합산 경로가 없는지
   확인**한다

## 감사 4 — 부록 1의 판정 기준과 반복별 Δp

### 질문과 정의

- Q4-1. [TASK25](TASK25.md)·[SIM_OOS_PREREG.md](SIM_OOS_PREREG.md)의 N=7
  `INCONCLUSIVE` 판정에 쓴 지표·정의·수치
- Q4-2. **예측 오차 허용치 `±0.05`와 방향 판정 밴드 `[0.97, 1.03]`은 다른 기준**이다.
  전자는 sim 대 실측의 게이트, 후자는 6블록 합산 재판정의 밴드
- Q4-3. 기존 3블록(b0–b2)과 신규 3블록(b3–b5)의 출처·seed·원자료 경로 연결
- Q4-4. N=7의 **6블록 각각**에 대해 `u_A`, `u_C`, `R = u_A/u_C`, `p_A`, `p_C`,
  `Δp = p_C − p_A`, 원 판정을 병기. **반올림된 `R`만으로 `Δp`를 역산하지 않는다** —
  `p`는 각 블록의 `[BUCKET]` 합계에서 직접 만든다
- Q4-5. 전체 합산과 배치별(기존/신규) 합산을 **구분**해 낸다
- Q4-6. [TASK50](TASK50.md)의 **단일 실행 쌍**과 **3실행 합산 쌍**의 채널 비 차이
  분포를 별도 절로 정리하고, **N=7의 원 판정 기준이 아니며 `Δp`의 변동 밴드도
  아님을 명시**한다

### Q4-7의 판정 규칙 (계산 전 고정)

논문이 "측정 변동 수준"이라 쓰려면 **`Δp`(또는 `R`)의 반복 간 변동을 같은 조건에서
직접 잰 자료**가 있어야 한다.

- 있으면 그 자료를 근거로 인용한다
- 없으면 **"사전 판정 기준에서 차이를 확정하지 못함"** 으로 수정안을 제시한다.
  [TASK50](TASK50.md)의 채널 비 분포는 **다른 양**이므로 이 근거로 쓰지 않는다
