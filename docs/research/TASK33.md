`(a) − (e)`가 **조율 자체의 몫**이다. 지식을 전부 줘도 세션끼리 합의하지 못하면 잃는 부분이며, **어떤 per-session runtime 정책도 이 부분에는 닿을 수 없다.**

### 정책의 비용 모형

`Informed`는 substrate가 실제로 물리는 두 항을 그대로 쓴다.

```
cost(τ) = prefill_s × running(τ)  +  generation_tokens × step_cost(k(τ)) / k(τ)
```

첫 항은 [TASK22](TASK22.md)의 배타 prefill 정지, 둘째 항은 [TASK13](TASK13.md)의 bucket 계단 비용이다. **채널을 끄면 그 항의 시간 의존성이 보이지 않는다** — 동료 정보가 없으면 `running(τ)`가 상수로 보이고, 생성 길이 정보가 없으면 batch가 줄어드는 것을 모른다.

### 정책 파라미터를 채널에 유리하게 튜닝했다

**초기 실행에서 `(c)`·`(d)`가 −10 %까지 나왔다.** 원인은 정책이 받는 `prefill_s`가 **전체 prompt** 기준이라는 데 있었다 — client는 자기 prefix가 아직 캐시에 있는지 알 수 없으므로 그것이 정직한 추정이지만, cache hit이 나는 반환에 대해 정지 항을 10배 과대평가해 정책을 과도한 대기로 몰았다.

**보정값을 고르는 대신 `prefill_scale`을 파라미터로 열고 `min_saving_s`와 함께 탐색 seed에서 전수 탐색(4 × 5 = 20조합)했다.** 그래야 음성 결과를 비용 모형 탓으로 돌릴 수 없다. 선택된 값은 대부분 `scale = 0`(정지 항 무시)이었다.

## 핵심 발견

1. **`class`(형태) — 현실 워크로드 headroom의 절반 이상은 *조율*이며 지식으로 살 수 없다.** `(a)−(e)`가 headroom의 중앙 60 %(49–73 %)다. 전지적 지식을 주고도 세션별로 따로 결정하면 그만큼 잃는다. **형태를 `class`로 보는 근거**: 이득이 "여럿이 같은 batch에 타는 것"에서 나오는 이상, 누가 어느 무리에 들지는 세션 하나가 자기 정보만으로 정할 수 없다. 이는 batch 경제성이 있는 어느 substrate에나 해당한다.
2. **`stack` — 남은 40 %도 실제 정보 채널로는 닿지 않는다.** `(e)`는 0.54–4.54 %를 얻지만 `(b)`·`(c)`·`(d)`는 최대 +1.16 %다. 격차는 **결과를 아는 것과 비용 모형으로 예측하는 것의 차이**다. 두 항짜리 모형은 실제 일정을 대신하지 못한다.
3. **`stack` — 생성 길이 채널은 반환 시각 채널보다도 값이 없다.** `(c)`가 9칸 중 −0.71 % ~ +0.14 %로 사실상 0이다. 정지 항을 피하려 기다리면 그만큼 좁은 batch로 decode하게 되어 두 효과가 상쇄된다.
4. **`universal` — 탐색 seed의 이득은 평가 seed에서 사라진다, 이번엔 4.32 % → −0.14 %.** [TASK27](TASK27.md)에서 34 % → 부호 반전으로 관측한 현상이 파라미터 수를 늘리자 더 커졌다. **자유 파라미터 2개, 20조합 탐색만으로도 5 %에 가까운 허구의 이득이 만들어진다.**
5. **`stack` — 따라서 runtime 회수 경로는 닫혔고 compile-time이 남는다.** 판정 분기가 사전 정의대로 `compile-time이 유일 회수 경로`로 확정됐다.

## 해석

- **(해석)** 발견 1이 이 연구선의 정책 질문을 닫는다. [TASK27](TASK27.md)이 "조정이 아니라 예지"라고 했는데, 현실 워크로드에서는 **예지도 아니고 조율**이다. 그리고 조율은 client 측 per-session 정책이 원리적으로 할 수 없는 일이다. **승인 범위가 client 측 보류로 한정된 것이 우연히 이 한계와 겹친다** — server 측 scheduler는 전 세션을 보므로 조율을 할 수 있다.
- **(해석)** 발견 2는 정책 설계의 한계를 정확히 짚는다. `(e)`와 `(d)`의 격차(예: ε=2·N=8에서 4.54 % 대 0.59 %)는 정보가 아니라 **그 정보를 결과로 바꾸는 모형**의 몫이다. 더 정교한 비용 모형이 그 격차를 줄일 수 있으나, 상한이 `(e)`이고 그마저 headroom의 40 %다.
- **(해석)** 발견 4는 방법론적으로 이 배치에서 가장 실용적인 교훈이다. 탐색/평가 분리를 하지 않았다면 `(b)` ε=5에서 "4.3 % 회수"라고 보고했을 것이고, 그것은 전부 허구였다.
- **(해석)** compile-time 경로가 남은 이유는 그것이 **조율을 설계 시점에 미리 굳히는** 방법이기 때문이다. bucket 격자와 slot 수는 모든 세션에 동시에 적용되므로 runtime 합의가 필요 없다.

## 확인되지 않은 사항

- server 측 scheduler가 조율을 수행할 때의 회수율 (`UNKNOWN`). 승인 범위 밖이며 patch 정책 대상이다.
- 더 정교한 비용 모형이 `(d)`와 `(e)`의 격차를 얼마나 줄이는지 (`UNKNOWN`). 상한은 `(e)`다.
- `(c)`가 왜 정확히 0 근처인지 (`PARTIAL`). 두 효과의 상쇄로 보이나 분리하지 않았다.
- 세 번째 정보 채널(캐시 상태) (`UNKNOWN`). client가 관측할 수 없어 다루지 않았다.
- 다른 워크로드에서 조율의 몫이 60 %인지 (`UNKNOWN`). 이 trace 하나다.

## 실패 / 무효 시도

- **첫 실행에서 `(c)`·`(d)`가 −5 ~ −10 %로 나왔다.** 정책에 준 `prefill_s`가 전체 prompt 기준이라 cache hit 시 정지 항을 크게 과대평가한 탓이었다. **보정값을 고르지 않고 `prefill_scale`을 파라미터로 열어 탐색 seed에서 전수 탐색**했고, 그래도 평가 seed 결과는 ≈0이었다. **음성 결과가 비용 모형의 산물이 아님을 이 절차로 배제했다.**

## 연구 원칙에 미치는 영향

1. **정보 분해에는 "결합 최적화를 뺀 전지" 수준을 반드시 넣는다.** 그것이 없으면 "정보가 부족하다"와 "per-session으로는 원리적으로 불가능하다"를 구분할 수 없다.
2. **채널을 끈다는 것은 값을 비우는 것이 아니라 존재를 없애는 것이다.**
3. **음성 결과를 보고하기 전에 자기 정책의 파라미터를 채널에 유리하게 전수 튜닝한다.** 그러지 않으면 정보의 값이 아니라 자기 설계의 품질을 잰다.
4. **자유 파라미터를 늘릴수록 탐색/평가 분리가 더 중요해진다.** 파라미터 2개로 5 %에 가까운 허구 이득이 생겼다.
