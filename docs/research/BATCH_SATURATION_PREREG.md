# 선등록 — `batch_size` 포화 곡선

## 문서 성격

[CLAUDE.md](../../CLAUDE.md) 실행 원칙 16과 [TASK_GUIDE.md](TASK_GUIDE.md)가 요구하는 **선등록(preregistration)** 이다. 이 문서를 담은 commit 이후에 compile과 측정을 시작한다.

## 연구 질문

**`batch_size`(= outer slot 수)의 device time 이득은 단조 증가하는가, 포화하는가, 반전하는가?**

[TASK35](TASK35.md)가 `batch_size` 8 → 16에서 +8.25 %를 확증했고 [TASK36](TASK36.md)이 그 이득이 **회수 가능한 캐시 손실의 잔량에 비례**함을 보였다. 그렇다면 "크게 할수록 좋다"가 성립하는가 — 이 TASK는 그 반론을 실측으로 봉쇄하거나, 봉쇄에 실패한다.

## 승인 범위 (사용자 판정, 2026-08-24)

재compile **최대 4회**(신규 2 + 진단 예비 2), 회당 **30분 상한**. `models/` 상한 **120 GiB**. serving 기동·종료 약 30회. 기존 관측 스택.

범위 밖: download, patch 변경, RSD 변경, remote push 자동 수행.

**예산 초과 신고**: 아래 격자는 serving lifecycle **36회**로 승인 추정치(약 30회)보다 6회 많다. 줄이려면 [TASK35](TASK35.md)의 B8·B16 측정을 재사용해야 하는데, 그러면 **1일 간격의 서로 다른 run을 곡선 위에 나란히 놓게 된다.** 이 곡선이 재려는 인접쌍 차이가 1 % 수준이라 run 간 표류가 신호와 같은 자릿수다. **내적 타당도를 위해 네 arm을 한 session에서 새로 잰다.**

### 눈금 통제 — 무엇이 통제되고 무엇이 통제되지 않는가

`decoder_batch_sizes`를 `(1, 4, 6, 8, 10, B)`로 고정하고 **최상위 눈금만 B로 바꾼다.** 중간 눈금 `4, 6, 8, 10`은 세 arm에서 동일하다.

| 인접쌍 | 무엇이 바뀌는가 | 통제 |
|---|---|---|
| B8 → B16 | `batch_size`(8→16) **와** 눈금 집합 전체(`(1,2,4,8)` → `(1,4,6,8,10,16)`) | **통제되지 않음** — 두 축이 함께 바뀐다 |
| **B16 → B24** | `batch_size`(16→24)와 **최상위 눈금 하나**(16→24) | **통제됨** |
| **B24 → B32** | `batch_size`(24→32)와 **최상위 눈금 하나**(24→32) | **통제됨** |

**B8 점은 기준(분모)이자 역사적 앵커이고, 포화 판정은 통제된 두 인접쌍에서만 내린다.** B8→B16의 축 분해는 이미 [TASK35](TASK35.md) 절제가 했다(batch +8.25 %, 눈금 +1.5 %p).

**B8에 `(1,4,6,8)` 계열 artifact를 새로 만들지 않는 이유**: B < 10이면 눈금 `10`이 존재할 수 없어 계열이 애초에 성립하지 않는다. 통제되지 않는 점을 통제된 것처럼 보이게 만드는 compile은 하지 않는다.

## 사전 검증 (compile 전, 중단 게이트)

### 게이트 1 — compile 예산 ([TASK10](TASK10.md) 모형)

| arm | bucket 수 | compiled model | 예측 compile | 예측 artifact |
|---|---|---|---|---|
| B24 | 6 | 7 | **472 s** (상한 1,800 s) | **13.11 GiB** |
| B32 | 6 | 7 | **472 s** | **13.11 GiB** |

`models/` 현재 **61 GiB** → 예측 **87.3 GiB** (상한 120 GiB). **통과.** 상한을 넘길 것으로 계산되면 B32를 포기하고 B24까지만 간다 — 이번에는 해당 없다.

### 게이트 2 — device 메모리 (산술 + **실측 앵커**)

산술: KV bytes/token = 147,456 B ([TASK05](TASK05.md)), slot당 `8192 × 147,456` = **1.125 GiB**, `num_devices=4`에 분산되어 **slot당 0.28125 GiB/device**.

**실측 앵커** (이 선등록 commit **이전**에 측정): `b16-mb16` artifact를 serving 상태로 올리고 `rbln-smi`를 읽었다 — **device당 6.6–7.0 GiB / 15.7 GiB**. B=16의 KV가 4.5 GiB/device이므로 **비-KV(가중치 + 그래프 + 활성) = 2.1–2.5 GiB/device**.

| arm | KV/device | + 비-KV(보수적 2.5) | 여유 (15.7 기준) | 판정 |
|---|---|---|---|---|
| B16 (실측) | 4.5 GiB | **6.6–7.0 GiB** | 8.7 GiB | — |
| B24 | 6.75 GiB | **≈ 9.25 GiB** | 6.5 GiB | load 예상 |
| B32 | 9.0 GiB | **≈ 11.5 GiB** | 4.2 GiB | **load 예상** |

**예측: B32도 load된다.** 다만 최상위 눈금의 decode 그래프가 폭에 따라 커지므로 비-KV 항이 위 추정보다 클 수 있다. **load에 실패하면 그 실패 자체를 결과로 기록하고 B24까지로 곡선을 그린다** — KV 한계의 실측 확인도 이 TASK의 산출물이다.

### 게이트 3 — 사상표 재검증 (각 신규 artifact, 본 측정 전)

동시성 **3, 5, 7, 9, 11**을 각 1회. **기대**: B24에서 3→4, 5→6, 7→8, 9→10, 11→24. B32에서 3→4, 5→6, 7→8, 9→10, 11→32.

사상이 기대와 다르면 그 자체를 기록하고 판정 설계를 조정한다.

## 채널

[TASK36](TASK36.md)의 교정된 정의를 **그대로** 쓴다.

| 채널 | 정의 |
|---|---|
| **A′** | `[BUCKET]` step 열 × [TASK13](TASK13.md) decode 비용 + per-request `prompt_tokens − cached_tokens` × [TASK22](TASK22.md) prefill 비용 |
| **B** | client `sent_s`/`done_s`의 in-flight 구간 합집합 (모형 무의존) |

허용차 `τ(N) = max(0.02, r_BASE / B_BASE)`, `r_BASE = B_BASE − A′_BASE`(그 N의 B8 arm). 구현은 [`config_device.py`](../../experiments/npu/analysis/config_device.py).

**알려진 편향을 명시한다**: 눈금 24·32의 step 비용은 [TASK13](TASK13.md)이 잰 범위(bucket 1·2·4·8) **밖으로 3–4배 외삽**한 값이다(`descriptor_for`의 최외곽 쌍 외삽: bucket 24 → 21.55 ms, 32 → 25.84 ms). **이것이 이 TASK 최대의 모형 불확실성**이며, 채널 B가 그 외삽에 의존하지 않는다는 것이 판정의 안전장치다. 아래 예측이 "최상위 눈금이 한 번도 쓰이지 않는다"고 말하므로 **예측이 맞으면 이 외삽은 판정에 영향을 주지 않는다** — 그 자체가 확인 대상이다.

### 곡선의 형태를 명시적으로 건다 — **B=16에서 포화(plateau), 반전 없음**

**등록하는 형태: 단조도 반전도 아닌 `포화`다.** B8 → B16에서 큰 이득이 나고, **B16 이후로는 평평하다.**

### 기전 분해 예측 (판정 아님, 기전 확인용)

| N | arm | 예측 생존율 | 예측 최상위 bucket 사용 빈도 |
|---|---|---|---|
| 6 | B8 / B16 / B24 / B32 | 16/18 / **18/18** / 18/18 / 18/18 | 24.5 % / **0 %** / 0 % / 0 % |
| 8 | B8 / B16 / B24 / B32 | 10/24 / **24/24** / 24/24 / 24/24 | 44.8 % / **0 %** / 0 % / 0 % |
| 10 | B8 / B16 / B24 / B32 | 1/30 / **29/30** / **30/30** / 30/30 | 43.1 % / **0 %** / 0 % / 0 % |

**포화의 기전은 두 겹이다.**

1. **생존율 포화** — B=16에서 이미 재사용이 100 %(N=10은 96.7 %)에 닿는다. 더 큰 pool이 살릴 캐시가 남아 있지 않다. [TASK36](TASK36.md)이 발견한 "이득은 회수 가능한 캐시 손실의 잔량에 비례한다"의 직접 귀결이다.
2. **최상위 눈금 미사용** — N ≤ 10에서 동시 decode 폭이 16·24·32에 닿지 않으므로 그 눈금은 **한 번도 선택되지 않는다.** 따라서 최상위 눈금의 큰 step 비용이 **부과되지도 않는다.** 반전이 나오려면 최상위 눈금이 실제로 쓰여야 하고, 그것은 N > 16에서나 가능하다.

**이 설계가 실제로 재는 것**: B16 → B24 → B32에서 최상위 눈금이 쓰이지 않는다면 세 arm의 차이는 **KV pool 크기와 `max_num_seqs` 뿐**이다. 즉 이 실험은 **"과잉 provisioning에 값이 붙는가"** 를 격리해서 묻는다. sim은 "붙지 않는다"고 답한다.

## 판정 기준

### 채널 일치 (모든 판정에 선행)

`|A′ratio − B ratio| ≤ τ(N)`. 넘으면 그 (N, arm)의 판정을 **보류**한다.

### 형태 판정 — 통제된 인접쌍 2개 (B16 vs B24, B24 vs B32)

각 인접쌍마다 **(N, block) 9칸의 per-cell ratio**(= 큰 B의 A′ / 작은 B의 A′)를 모집단으로 삼아 **중앙 ratio의 percentile bootstrap CI**를 구한다([CLAUDE.md](../../CLAUDE.md) 원칙 17).

- resamples **4,000**, `alpha = 0.05`, base seed **20261200**
- 사전 등록 **CI 폭 상한 = 0.04**

| CI 위치 | 판정 |
|---|---|
| 1을 포함 **and** 폭 ≤ 0.04 | **포화** |
| 전부 1 초과 | **반전** — 더 키우면 손해다 |
| 전부 1 미만 | **계속 이득** |
| 1을 포함하나 폭 > 0.04 | **INCONCLUSIVE** |

**두 인접쌍이 모두 `포화`이면 등록한 형태가 확인된 것이다.** 하나라도 `반전`·`계속 이득`이면 **등록한 형태는 틀린 것이며 그렇게 기록한다.** 특히 **`계속 이득`이 나오면 sim의 포화 예측이 틀렸다는 뜻이고, 그 원인 규명이 후속 TASK가 된다.**

### 부속 판정 — 기전 분해

1. **생존율**: B16·B24·B32의 실측 생존율이 세 arm에서 같고 B8보다 높은가.
2. **최상위 눈금 빈도**: B16·B24·B32에서 최상위 눈금(16·24·32)의 step 비중이 **0 %인가.** 0이 아니면 예측된 기전이 틀린 것이며, 그때는 외삽된 step 비용이 채널 A′ 판정에 개입한다는 뜻이므로 **채널 B를 우선 채널로 승격해 보고한다.**

### B32 load 실패 시

B32의 36칸 중 해당 12칸을 `실행 불가`로 기록하고, 곡선을 B24까지로 그린다. **`INVALID`가 아니라 결과다** — KV 한계의 실측 위치가 산출물이다.

## 불변식 (fail-loud, 위반 조합은 `INVALID`)

- **P1**: 네 arm의 plan이 동일
- **P2**: 네 arm의 decode 작업량 `Σ(completion_tokens − 1)`이 동일
- **P3**: 각 arm의 `[BUCKET]` padded 값이 그 arm의 bucket 집합 안에만 있다
- I1–I5: [NSLOTS_SWEEP_PREREG.md](NSLOTS_SWEEP_PREREG.md)와 동일

## 필수 측정 항목

조합별: per-request JSONL, plan summary, `[BUCKET]`·`[PFX]` 로그 전문, `/metrics` 덤프, utilization JSON. 신규 artifact마다: compile 로그·wall-clock·크기·`rbln_config.json`·사상표·**load 직후 `rbln-smi`**. 전체: patch state, `rbln-smi` 시작·종료, provenance, 측정 시각, 선등록 commit.

## 실행 절차 (측정 전 고정)

`<RUN>` = `results/npu/stage2/<timestamp>-batch-saturation`

1. `apply.sh status` → `patched` 확인, 32/32 idle 확인
2. B24 compile → 비용 실측 → load → `rbln-smi` → 사상표
3. B32 compile → 비용 실측 → load → `rbln-smi` → 사상표. **load 실패는 기록하고 계속 진행**
4. N 6 → 8 → 10, 블록별 arm 순서표대로 36조합. background + 완료 표식 + PID 기준 종료
5. 조합마다 `utilization.py`(arm별 `--buckets`)
6. P1–P3·I1–I5 → 채널 일치 → bootstrap 형태 판정 → 기전 분해

블록 랜덤화: b0 B8→B16→B24→B32 / b1 B24→B32→B8→B16 / b2 B32→B8→B16→B24.

**실행 중인 실험의 script를 편집하지 않으며, 진행 중인 run을 감사하지 않는다.**
