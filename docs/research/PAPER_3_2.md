# 논문 3.2용 문장·표·주석

이 문서의 본문·표·캡션에는 **내부 작업 번호, 내부 작업명, 원로그 경로를 넣지
않는다.** 근거 연결은 [PROVENANCE_3_2.md](PROVENANCE_3_2.md)가 보존한다.

용어는 계층 번호로 쓰지 않고 의미로 쓴다 — **128-token prefix 관리 단위**와
**8,192-token KV slot**.

---

## 3.2.1 두 관리 단위와 관측 채널

본 스택의 KV는 두 단위로 관리된다. 상위 서빙 엔진은 prefix를 **128-token 단위**로
관리하고, 가속기 런타임은 시퀀스 하나분의 KV를 **8,192-token slot** 하나에 담는다.
기준 구성에서 slot은 8개이며, 그 수는 compile 시점의 `batch_size`가 정한다.

두 단위는 재사용의 서로 다른 국면을 정한다. **재사용의 성립 여부는 slot이
결정하고**(slot이 회수되면 그 시퀀스의 prefix는 통째로 사라진다), **성립했을 때
보고되는 양은 128-token 단위로 내림된다.** 그래서 한 요청이 재사용한 token 수는
언제나 128의 배수이고, 그 값이 0이 되는 사건은 slot 회수다.

관측 채널을 이 구분에 맞춰 선택한다. 엔진의 누적 prefix-cache hit counter는
**128-token 단위 장부의 판단**이며, slot이 이미 회수된 뒤에도 hit을 계속 보고한다.
본 논문은 이 counter를 재사용 지표로 쓰지 않는다. 대신 **응답에 실려 오는 요청별
cached token 수**를 쓴다. 이 값은 요청 단위로 귀속되므로 동시 실행에서도
다른 요청의 기여가 섞이지 않는다. 동시 실행 중 누적 counter의 차분을 개별 요청
값으로 쓰는 것은 본 논문 어디에서도 하지 않는다.

## 3.2.2 재사용 범위

재사용이 관측된 요청의 cached token 수는 **직전 요청이 prefill로 계산한 범위를
128-token 단위로 내림한 값**과 일치한다. 직전 요청이 decode에서 생성한 token은 이
범위에 들어가지 않는다. 따라서 이하에서 "KV 생존"은 **직전 요청의 prefill 범위가
재도착 요청에서 재사용되는 상태**를 뜻하며, 이전 문맥 전체의 재사용을 뜻하지 않는다.

## 3.2.3 생존 문턱

대상 세션의 도구 대기 구간에 도착한 배경 요청 수를 m으로 둔다. m은 실험 전체의
동시 세션 수와 다른 값이며, 대상 KV가 재사용되기 전까지 노출되는 요청 압박을
나타낸다. 배경 요청은 각각 2,000 token으로 서로 유일하고, 대상 요청 → 배경 m건 →
재도착 요청을 **동시성 1로 순차 전송**한다.

slot 8개 구성에서 **m ≤ 6이면 대상 KV가 모두 재사용되고, m ≥ 7이면 모두
재사용되지 않는다.** 이 전환은 m ∈ {5, 6, 7, 8}을 각 3회씩 실행한 **12개 실행
전부에서 동일**하게 나타났다 — m ≤ 6의 6개 실행이 전량 재사용, m ≥ 7의 6개 실행이
전량 미재사용이다. 부분 생존 구간은 관측되지 않았다.

이 결과는 대기 시간이 길어지는 만큼 재사용량이 점진적으로 줄어드는 형태와 다르다.
재도착 전까지 이전 prefill 범위가 남아 있으면 그 범위를 재사용하고, 회수되면 그
범위를 다시 계산하는 **불연속적인 변화**다.

문턱 근처에서는 무처치 반복만으로도 결과가 흔들린다. 동시 세션 8개의 같은 계획을
10회 반복했을 때 **3회에서 재사용 성공이 8건 중 5건, 나머지 7회에서 6건**이었다.
고정한 배경 요청 조건에서 관측한 문턱의 재현성이, 실행 시각과 요청 중첩이 달라지는
모든 조건에서 개별 세션의 생존까지 고정한다는 뜻은 아니다.

## 3.2.4 회수 순서와 회수 건수

본 스택의 slot 회수는 **FIFO**이며 재접근이 회수 순위를 갱신하지 않는다. 따라서
KV가 최근에 재사용되었다는 사실만으로 회수가 늦춰지지 않는다. 생존 여부를
해석하려면 대기 시간뿐 아니라 **대상 KV의 회수 순위와 재도착 전까지 발생한 후속
할당**을 함께 보아야 한다.

한 실행에서 일어난 회수 건수는 **요청 할당 건수만으로는 맞지 않는다.** 요청은
`m + 2`건(대상 1 + 배경 m + 재도착 1)이고 slot은 8개이므로 순진한 산술은
`max(0, m + 2 − 8)`을 예측하지만, 관측은 언제나 **한 건 더 많다.** 그 한 건은
**decode batch가 compiled 폭을 채우지 못할 때 스케줄러가 padding용 scratch로 집는
slot**의 몫이다. 이 경로는 slot 하나를 확보하기 위해 회수를 유발하면서도 그 slot을
요청에 할당하지는 않는다. 수요를 하나 더 세면

> 회수 건수 = `max(0, (요청 수 + 1) − slot 수)`

가 되고, 이 식은 **21개 실행 전부에서 정확히 맞는다**(요청 수 2–51, 회수 0–44).

이 사실은 본 논문의 두 기전이 **같은 자원에서 만난다**는 것을 뜻한다. 배치 격자의
padding은 계산 시간을 낭비할 뿐 아니라, pool이 포화한 순간에는 **살아 있던 prefix
하나를 회수시키는 대가**를 함께 치른다.

문턱 자체는 이 산술식이 아니라 **순서**가 정한다. m = 6에서는 재도착 요청의 조회가
먼저 성립하고 회수가 그 뒤에 일어나 재사용이 성공한다. m = 7에서는 재도착 요청의
할당이 대상 KV를 먼저 회수하므로 조회 시점에 대상이 이미 없다. 따라서 본 절은
**생존 문턱의 존재와 그 급격함을 보고하되, 문턱의 위치를 예측하는 산술식이
검증되었다고 주장하지 않는다.**

도착 순서에 따른 개별 생존 차이는 동시 세션 8개를 고정하고 재개 도착 순서만 바꾼
비교에서 관측된다 — 6개 조건 중 5개에서 **더 이른 도착이 더 자주 재사용에
성공**했고, 분산이 큰 조건에서는 3개 블록 모두 가장 이른 두 도착이 성공했다. 이
비교는 상관계수나 유의성 검정을 동반하지 않으며, **순서 의존성을 뒷받침하는
관측으로 한정**한다.

## 3.2.5 용량 개입

고정된 slot 수가 재사용 실패에 관여한다면, 동일한 입력 계획에서 slot을 더 제공할 때
생존이 개선될 것이다. 이를 시험하기 위해 compile 시점의 `batch_size`를 **8에서
16으로** 바꾼 구성을 만들었다. 본 실행 경로에서는 slot 수가 그 값과 같으므로
slot도 8개에서 16개가 된다.

동시 세션 8개, 같은 입력 계획 3회 반복에서 **재사용에 성공한 재도착 요청이 24건 중
9건에서 24건 전부로 늘었다.** 재계산해야 했던 prefill token은 재도착 요청 기준
**22,103에서 5,079로(−77.0 %)**, 전체 요청 기준 **50,736에서 33,712로(−33.6 %)**
줄었다.

다만 `batch_size`는 slot 수뿐 아니라 **실행 batch 상한**도 바꾸는 인자다. 따라서
이 개입은 slot 수만을 독립적으로 조작한 실험으로 해석하지 않는다. 두 구성의 실제
배치 격자와 실행 분포를 함께 보고한다 — **새로 추가된 폭 16은 이 워크로드에서 한
번도 선택되지 않았고**(관측된 최대 동시 실행 폭이 8이다), **공통 폭의 사용 분포는
완전히 같지는 않다**(폭 4와 8의 step 수는 정확히 같고, 폭 1과 2에서 각각 45 step
증가·15 step 감소했다).

또한 이 생존율 비교만으로 문턱이 몇 요청만큼 이동했는지는 확정할 수 없다. 변경된
구성에서 배경 요청 수별 전환 위치를 별도로 측정한 경우에만 문턱 이동을 보고한다.

## 3.2.6 재계산 작업량으로의 연결

KV가 생존한 재도착 요청도 직전 decode가 생성한 token과 새로 이어붙인 token은
prefill로 계산해야 한다. KV가 재사용되지 않은 요청은 여기에 더해 **직전 요청의
prefill 범위까지 다시 계산**한다.

따라서 재도착 요청의 token 수가 같을 때, 재사용 실패로 추가되는 prefill 작업량은
**생존 시 재사용할 수 있었던 token 수**에 해당한다. 본 워크로드의 직전 prefill
범위는 800–1,600 token이고 재사용 가능한 양은 그것을 128-token 단위로 내림한
**768–1,536 token**이다.

이 추가 작업량에 prefill 비용 모형을 적용한 값이 비용 모형의 재계산 항에 반영된다.
추가 prefill 자체의 계산 비용과, 그 prefill이 다른 세션의 decode 실행을 지연시키는
영향은 구분한다. 후자는 별도의 절에서 다룬다.

## 3.2.7 이 절이 확립한 것

1. 재도착 요청이 실제로 재사용하는 범위는 **직전 요청의 prefill 계산분을 128-token
   단위로 내림한 부분**이며, 그 범위의 생존 여부가 재계산 작업량을 **불연속적으로**
   바꾼다.
2. 기준 구성에서 배경 요청 수에 따른 **생존 문턱**이 관측되었고(m ≤ 6 전량 생존,
   m ≥ 7 전량 소멸, 12개 실행 일치), slot 수를 늘린 구성에서 재사용이 **9/24에서
   24/24로** 개선되었다.
3. 한 실행의 회수 건수는 **요청 수보다 하나 많은 수요**를 세어야 맞으며, 그 하나는
   **배치 padding용 scratch slot**이다. 배치 격자와 KV 용량은 독립적인 두 축이
   아니라 같은 pool을 공유한다.
4. 문턱의 정확한 산술과 slot 수만의 독립적인 효과는 현재 실험에서 확정하지 않았다.
5. 이 기전은 **시퀀스 단위 고정 용량과 FIFO 회수**를 쓰는 본 실행 경로에서 확인한
   결과다. 다른 attention 구현이나 회수 정책에 같은 문턱을 그대로 적용할 수 없으며,
   같은 자원 구조와 회수 정책을 쓰는 구성에서의 재현 가능성은 별도의 검증 대상이다.

## 표

### 표 3.2-A. 두 관리 단위

| | prefix 관리 단위 | KV slot |
|---|---|---|
| 크기 | 128 token | 8,192 token |
| 개수 (기준 구성) | 512 | **8** |
| 회수 정책 | LRU | **FIFO** |
| 할당 단위 | prefix 조각 | **요청 1건 = slot 1개** |
| 재사용에서의 역할 | 보고되는 **양**을 양자화 | 재사용의 **성립 여부**를 결정 |

**주석**: 개수는 기준 구성의 값이며 KV slot 수는 compile 시점 `batch_size`와 같다.
동일 계열 하드웨어라도 compile 구성이 다르면 달라진다.

### 표 3.2-B. 회수 건수 (실행당)

| 배경 요청 수 m | 요청 수 | 관측 회수 | 요청 할당만 센 예측 | padding scratch를 더한 예측 |
|---|---|---|---|---|
| 0 | 2 | 0 | 0 | 0 |
| 3 | 5 | 0 | 0 | 0 |
| 5 | 7 | 0 | 0 | 0 |
| 6 | 8 | **1** | 0 | **1** |
| 7 | 9 | **2** | 1 | **2** |
| 8 | 10 | **3** | 2 | **3** |
| 9 | 11 | 4 | 3 | 4 |
| 16 | 18 | 11 | 10 | 11 |
| 33 | 35 | 28 | 27 | 28 |
| 49 | 51 | 44 | 43 | 44 |

**주석**: 21개 실행(위 10개 조건, m ∈ {5,6,7,8}은 각 3회)에서 오른쪽 열이 전부
맞고 왼쪽 열은 회수가 0인 5개 실행에서만 맞는다. 회수 사건 자체에는 유발자를
식별하는 표시가 없다. padding scratch로의 귀속은 (i) 선점 경로가 한 번도 발생하지
않았고, (ii) 실행마다 정확히 한 건의 회수만 그 slot이 끝내 재할당되지 않으며,
(iii) 소스에서 할당 없이 회수만 하는 경로가 그것 하나라는 소거법에 근거한다.

### 표 3.2-C. 용량 개입 (동시 세션 8, 3회 반복)

| 구성 | slot 수 | 재사용 성공 | cached token | 재계산 prefill token (재도착분) | 최대 실행 폭 |
|---|---|---|---|---|---|
| 기준 | 8 | **9 / 24** | 9,856 | 22,103 | 8 |
| 용량 확대 | 16 | **24 / 24** | 26,880 | **5,079** | 8 |

**주석**: 두 구성의 입력 계획은 3회 반복 전부에서 요청 길이 열과 도구 대기 총량이
동일하다. `batch_size`는 slot 수와 실행 batch 상한을 함께 바꾸므로 slot 수만을
분리한 개입이 아니다. 새로 추가된 실행 폭 16은 이 워크로드에서 한 번도 선택되지
않았으나, 공통 폭의 사용 분포가 완전히 같지는 않다.
