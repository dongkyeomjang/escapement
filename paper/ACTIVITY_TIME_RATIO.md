# 비용 모형 없는 관측 활동 시간 비 (지시문 16 작업 B, TASK110)

판정 종류: **post_hoc**. 측정 0, 기존 run 로그만 읽음. 기존 판정 변경 없음.
스크립트: `experiments/npu/analysis/activity_time_ratio.py` → `results/npu/stage3/activity_time/activity_time.json`(ignored raw).

## 1. 정의

모집단은 A′와 같다(`mt_measure.lifecycle_metrics`): 평가 구간 요청(`w0 ≤ sent_s < w1`, 120 s)과, 그 요청들의 첫·마지막 ALLOC 사이의 `[BUCKET]` 줄. A′는 이것을 TASK13 decode·TASK22 prefill 비용 모형으로 값을 매기고, 여기서는 관측 시간으로 바꾼다.

| 항 | 정의 | 출처·단위 |
|---|---|---|
| decode step 시간 | TASK91 귀속: 요청 R의 ALLOC–FREE 사이 `[BUCKET]` 줄이 R의 decode step. R의 k번째 줄 step = R 스트리밍 chunk `t[k+1] − t[k]`(client 시계, s). (k−1)–k번째 줄 사이에 ALLOC이 없으면 **깨끗함**. step을 덮는 실행 요청 중 아무나 귀속 가능(깨끗한 것 우선) | client `tokens.*.jsonl.gz`, server log |
| 귀속 불가 step | 깨끗한 구간이 없는 step(구간 안에 prefill이 있거나, 귀속 가능한 실행 요청이 없음). 시간은 같은 lifecycle·같은 `request_nums`의 깨끗한 구간 중앙값으로 채움(없으면 lifecycle 전체 중앙값) | 채움 값 = 관측값의 중앙값, 비용 모형 아님 |
| prefill `srv` (주) | 평가 구간 요청 수 × run 종료 요약 `PREFILL METRICS` 평균 지연(model forward, run 전체 prefill 호출 평균, 워밍업 포함) | server log `metrics.py` 요약, ms. 호출 수 = ALLOC 수(30/30 cell 일치) |
| prefill `exc` (대안) | ALLOC이 귀속 구간 안의 유일한 ALLOC인 요청: 구간 − 그 step의 채움 decode 시간(이 기판에서 prefill은 배타적). 나머지 요청은 `srv` 평균 | client 시계, s |
| 활동 시간/turn | (decode 합 + prefill 합) / 평가 구간 요청 수 | s/turn |
| 비 | 같은 replicate의 구성/BASE, 판정이 쓴 lifecycle(verdict `selection`). 중앙값과 최소–최대 | 무차원 |

요청별 `prefill elapsed`는 server log에 없다(`PREFILL METRICS`·`DECODE METRICS`는 종료 시 두 번 — model과 `[SAMPLER]` — 나오는 run 전체 요약뿐).

## 3. 차이의 관찰 (관찰과 해석 분리)

관찰:
1. `exc` 비는 A′ 비와 20 cell 모두 0.025 이내(중앙 차 절댓값 0.000–0.024). `srv` 비는 N ≥ 13 config cell 14개 중 12개에서 A′보다 0.018–0.058 크다(감소 폭이 작게 나옴); N13은 −0.007/−0.002.
2. A′ 비 중앙값이 관측 비의 replicate 최소–최대 밖인 cell: `exc` 2/20(TASK82 N8 BATCHONLY 0.980 대 [0.981–0.998], N8 TUNED 0.972 대 [0.985–1.008]), `srv` 6/20(TASK82 N8 TUNED, TASK87 N16 두 구성, TASK95 N17 두 구성, TASK102 N18 TUNED). 범위끼리 겹치지 않는 cell: `exc` 1(TASK82 N8 BATCHONLY), `srv` 2(TASK95 N17 두 구성).
3. 저부하(TASK82 N6·8·10)에서 관측 비 − A′는 `srv` −0.006–+0.014, `exc` +0.008–+0.024; N6 BATCHONLY는 관측 1.004·1.008 대 A′ 0.990으로 1을 사이에 둔다.
4. decode만의 비는 N20을 빼면 0.97–1.11(구성의 decode 시간/turn이 BASE와 비슷하거나 더 큼). 감소는 prefill 쪽에서 온다: 예) TASK102 N18 prefill/turn `exc` BASE 0.305 s 대 TUNED 0.124 s.
5. `srv`와 `exc`의 prefill 평균: 고부하 BASE에서 `exc` > `srv`(예: TASK102 N18 291–308 대 286 ms), BATCHONLY·TUNED에서 `exc` < `srv`(116–117 대 138 ms). TASK102 N18 r0 점검: BASE `exc` 평가 구간 305.0 ms(190건)·구간 밖 269.0 ms(132건), `srv` 284.6 ms; TUNED r0 `exc` 구간 118.8·밖 117.0 ms, `srv` 128.4 ms; TUNED r1 구간 115.1·밖 127.6, `srv` 138.7 ms.

파생 해석(확인 범위 표시):
- `srv`가 감소 폭을 작게 보이는 원인 후보 두 가지. (i) **기간 차**: `srv`는 run 전체 평균이라 평가 구간과 prompt 길이 구성이 다른 워밍업이 섞인다 — BASE는 구간 안 prefill이 밖보다 크다(r0에서 확인). (ii) **모집단 차**: `exc`는 decode와 겹친 prefill만 덮는다; TUNED에서 `srv` > `exc`가 구간 안·밖 모두에서 나타나므로, `exc`가 덮지 못한 prefill(엔진이 쉬는 동안의 prefill, 한 구간에 ALLOC 2개 이상)이 더 클 가능성. 두 원인의 몫은 분해하지 않았다(**UNKNOWN**).
- `srv`는 model forward 지연만이고 `exc`는 step 간격(host overhead 포함)이라 시계 정의가 다르다; decode 시간(step 간격)과 같은 시계인 쪽은 `exc`다.
- 귀속 불가 step(최대 6.3 %)은 대부분 prefill을 품은 step이며, 채움은 같은 `request_nums`의 깨끗한 구간 중앙값이라 그 step의 decode 몫만 넣는다(prefill 몫은 prefill 항에서 셈). 채움 방식이 비에 주는 영향은 이 비율 이하의 step에 한정된다.

## 4. 한계

- 요청별 prefill 경과시간이 없어 prefill은 대리값이다. `srv`는 run 전체 평균(워밍업 포함, model forward만), `exc`는 decode와 겹친 prefill만 직접 관측(나머지는 `srv`).
- step 시간은 client 시계(스트리밍 chunk 간격)이며 네트워크·직렬화 지연을 포함한다.
- 주 대리값(`srv`)은 결과를 보기 전 스크립트에 정했다. `exc`가 A′와 더 가깝다는 것은 결과를 본 뒤의 관찰이다.
